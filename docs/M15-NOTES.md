# M15: the PDF reader never worked, and the checks that catch that

Overlay onto M14:

    cp -r harbor/. /path/to/harbor/
    cd /path/to/harbor && npm install && npm run verify
    harbor dev preflight
    harbor dev extract

No migration.

## Every PDF receipt in your mailbox has been skipped

`pdf-parse` bundles a pdf.js from 2016 and fails with "bad XRef entry" on any
PDF using a cross-reference stream, which is almost every PDF made in the last
decade. Verified before changing anything: it rejects a plain three-line receipt
generated by a stlarkspurd library, and `unpdf` reads the same file correctly.

The way it failed is the important part. It did not crash a sync, it did not
report a missing dependency, and nothing anywhere said a word. It recorded the
attachment as unreadable and moved on, which is a legitimate outcome for a JPEG,
so the pipeline treated a total failure as an ordinary skip. `harbor purchases`
being empty was the only symptom, and that has a dozen other explanations.

I had also told you attachments were "referenced but not fetched" and that this
would be a milestone of work. That was wrong. The IMAP connector parses them,
the engine stores them, and extraction already reads their text. The only broken
part was the PDF reader, which is one dependency.

## `harbor dev preflight`

A separate command from `doctor` on purpose. `doctor` answers "is my Harbor
healthy", which a person asks. This answers "is this installation wired up
correctly", which somebody asks after changing the installation.

It exists because every serious failure in the last week lived outside the
process: a declared dependency missing from `node_modules`, a log path the
instructions did not name, a keychain entry holding a key that opened nothing, a
service manager that never reads a shell profile, a status line asserting
something it had not checked. Typecheck cannot see any of that. The build cannot
see it. Every test passed through all five.

    harbor dev preflight

- every declared dependency actually resolves
- the store's paths exist and are writable
- `dist/cli/main.js` is built, since the service manager points at it
- every key Harbor might use, and whether it opens the store
- an installed service, and whether it is running or crash-looping
- backups, by age

The bar for adding a check: it must be able to be true in development and false
on a real machine.

## `harbor settings encryption --repair-keychain <key>`

Recovering from a bad keychain entry took four commands and a `while` loop.

It verifies the key opens the store *before* touching anything, deletes until
there is nothing left to delete (one `delete-generic-password` removes one item,
and a surviving duplicate was the whole original fault), writes, reads back, and
compares. A wrong key is refused rather than stored.

## 0.36.1

The keychain entry for the store key was replaced three times by a random key
that opened nothing, each time at the exact second an ordinary command ran:
`harbor doctor` at 09:11:20, `harbor --version` at 09:20:49, `harbor dev
preflight` at 09:38:40. Not a clock, not a rebuild.

I could not find the cause. `encryptStore` and `repairKeychain` are the only
writers of that item in the whole codebase, `encryption.ts` is the only file
that generates 64 hex characters of randomness, and neither had run. Account
credentials are filed under `sourceType:label`, keychain detection only runs
`security help`, and credential warming reads.

So instead of guessing a fourth time:

**`saveKey` refuses a key that does not open the store.** One read, and it
closes the class regardless of what is writing or why. A key that cannot open
the file was never worth keeping.

**Every attempt is recorded in `logs/keychain.log`**: timestamp, accepted or
refused, the first eight characters of the key, the pid, and the command line.
Outside the database on purpose, since the database is the thing that cannot be
opened when this goes wrong. The next occurrence will name itself.

This does not fix whatever is doing it. It means whatever is doing it can no
longer lock you out, and leaves evidence behind.
